# 产品宣传视频

产品宣传视频不是“把功能截图做得很炫”。它要在目标用户愿意停留的时间内，讲清一件真实的事：**谁在什么场景下，为什么应该现在用这个产品，以及下一步该做什么。**

本 Skill 先完成发布判断，再做可复现成片：`发布 brief → 证据与镜头脚本 → 静帧审阅 → MP4 → 发布验证`。输出可以用于官网、发布会、应用商店或社媒；不同渠道不是同一条视频裁成不同尺寸。

## 输入与边界

优先使用用户提供的产品链接、真实截图、录屏、品牌资料、功能说明、发布目标、目标受众和 CTA。信息不完整时，先分析产品公开页面并形成标注假设的 brief；涉及产品价值、数据、用户评价或功能细节时，不确定就不写进成片。

- 界面必须来自用户提供的真实截图/录屏或产品公开页面；不画不存在的产品界面。
- 数字、客户、用户评价和兼容性声明必须有用户材料、官方页面、财报、应用商店或其他可追溯来源。查不到就不使用“数据证明”场景。
- 不拿同一段素材硬做所有渠道：先明确投放位置、时长、画幅、是否静音观看及 CTA。
- 为他人产品制作的作品只作为演示、提案或获授权的发布物；不要暗示为官方成片。
- 合成配乐仅用于预览或内部使用；正式发布必须由发布方确认音乐、肖像、商标与素材授权。

## 第一步：先做发布判断

在选择动效风格或开始抓网页前，先回答以下问题。信息缺失时给出最小的暂定判断，并用 `[待确认]` 标记。

| 要判断什么 | 需要得到的答案 |
| --- | --- |
| 目标 | 是下载、试用、预约、理解新功能、品牌认知，还是销售转化？ |
| 受众 | 谁正卡在什么具体任务；他们最在意的代价或结果是什么？ |
| 单一承诺 | 视频只要让观众记住的一件真实价值是什么？ |
| 证据 | 哪张真实界面、录屏、数据或公开事实能证明这项承诺？ |
| 渠道 | 官网/发布会、应用商店、信息流、社媒自然传播的时长与画幅是什么？ |
| 行动 | 看完后立刻做什么：访问、下载、注册、预约、搜索还是联系销售？ |

不要把“功能很多”当成承诺。若一个视频同时要讲多个受众或多个产品线，先建议拆成系列视频，而不是堆成一条功能目录。

## 第二步：把卖点变成可拍的证据链

读取 [发布 brief 与证据表](references/release-brief-template.md)，先完成：

`用户情境 → 核心阻碍 → 产品动作 → 可见结果 → 下一步行动`

一项卖点必须同时有：

1. **产品事实**：它实际能做什么；
2. **可见证据**：真实截图、录屏关键帧、可追溯数据或明确演示；
3. **用户结果**：节省什么步骤、减少什么风险、完成什么任务；
4. **表达边界**：哪些是已证实事实，哪些只是发布假设。

先决定叙事，再选择素材。不能被证明的卖点，不要写进旁白；只有“产品很好”的素材，不要占据主要镜头。

## 第三步：按渠道制作镜头脚本

读取 [镜头脚本模板](references/storyboard-template.md)。默认结构按渠道调整：

| 渠道 | 建议时长 | 开场 | 中段 | 结尾 |
| --- | --- | --- | --- | --- |
| 信息流 / 短视频 | 15-25 秒 | 0-3 秒直接给场景或结果，品牌同步出现 | 2 个可见证明 | 单一 CTA |
| 官网 / 产品发布 | 30-45 秒 | 一句产品承诺 + 品牌 | 2-3 个任务场景与证据 | 价值回收 + CTA |
| 应用商店 | 15-30 秒 | 真实任务与界面 | 按真实使用流程展示 | 下载 / 安装提示 |
| 发布会 / 销售演示 | 45-60 秒 | 为什么现在需要它 | 重点功能、成果与可信事实 | 下一个行动或联系路径 |

镜头脚本必须逐场写清：画面、屏幕文字、旁白、使用的真实素材、它证明什么、时长和转场。屏幕文案是关键词，旁白补充逻辑，二者不要逐字重复。

## 第四步：生成并校验 brief

1. 使用 `assets/brief.template.json` 建立 brief；其中 `campaign` 和每场的 `evidence` 是发布判断层，渲染器会忽略它们，但校验器会检查；
2. 真实截图、logo 与录屏关键帧放入 `brand/`，不要拿带背景的宣传图代替 logo；
3. 运行 `python3 scripts/validate_brief.py brief.json`；修复缺少目标、受众、CTA、证据来源或数据出处的问题；
4. 运行 `python3 scripts/check_environment.py`。静帧需要 Node 和 Chrome/Chromium；完整 MP4 还需要 ffmpeg。若本机缺少 ffmpeg，先完成静帧审阅并明确告知用户，不能假装已经出片；
5. 在 `scripts/` 目录运行 `npm install --silent`（首次需要），然后先运行 `python3 make.py brief.json --preview`；
6. 查看每场静帧：文字是否溢出、截图是否清晰、logo 是否可见、信息是否能在静音状态下理解、证据是否真的支持旁白；
7. 静帧通过后，运行 `python3 make.py brief.json`。需要竖版时显式用 `--format 9:16`，不要只裁切横版；
8. 从 `timeline.json` 抽取开场、证据镜头、转场和结尾帧复核。发现问题，回到脚本或素材层修改后再渲染。

已有真实官网可用作素材线索时，可运行：

```bash
cd scripts
node fetch_brand.mjs https://example.com <工作目录>/brand
```

抓到的 logo、页面截图和图片只是候选素材。先检查它们是否真实、与脚本对应、没有登录弹窗或过期信息，再进入 brief。

## 风格只服务于发布目的

渲染器提供 `apple-keynote`、`saas-glow`、`kinetic`、`flat-mg`、`editorial`、`neo-brutal`、`cyber-glitch`、`bento` 等动效风格。选择标准是产品调性与渠道：

- SaaS、AI、开发者或 B 端产品优先 `saas-glow` / `bento`；
- 消费 App、教育和社区优先 `flat-mg`；
- 信息流、活动预热和年轻品牌可用 `kinetic`；
- 高端硬件或旗舰发布可用 `apple-keynote`；
- 媒体、文化或生活方式产品可用 `editorial`。

用户没有指定风格时，先根据渠道和产品气质选择一个最匹配的版本。只有用户明确需要比较时，再出 2 个差异足够大的版本，不为展示风格而批量渲染。

## 交付

交付的不只是 MP4。需要一并给出：

1. 成片路径、时长、画幅、实际配音引擎与配乐状态；
2. `brief.json`、`index.html`、静帧、`timeline.json` 和原始素材目录，保证可修改与复现；
3. 视频中每个关键承诺对应的证据来源；
4. 发布说明：投放位置、CTA、假设、首轮观察指标与判定规则。

例如，信息流视频不能只看播放量；需预先说明用 3 秒留存/完播、落地页点击、安装或试用转化中的哪一项判断开场、承诺或 CTA 是否需要重做。

## 质量门槛

- 前 3 秒能看出产品为谁解决什么问题；
- 全片只有一个核心承诺，最多 2-3 个证据镜头；
- 每项数字与关键事实可追溯；
- 静音看也理解大意，声音打开后获得额外解释；
- 真实 UI、logo 和 CTA 清晰，不被字幕或装饰遮挡；
- 发布方能根据交付物继续改片，并知道发布后看什么信号决定迭代。
