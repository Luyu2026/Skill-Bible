# 项目找赛与参赛执行

把一个已有项目推进到符合官方要求、取得可核验提交记录的参赛状态。项目可以是 Skill 集合、软件、网站、工具、内容作品或研究成果。用户说“找合适的比赛并直接参赛”时，持续推进材料准备和正式提交；候选赛事表只是中间产物。

## 输入与启动

优先读取用户给出的仓库、项目页面、现有文件、可用演示和已有参赛记录。没有指定项目时，只补问项目入口或一句能力介绍。联系人、职业、年龄、所在地、公司/学校等事实不猜测；仅在当前表单确实需要且已有信息不足时询问。

按原请求区分：只调研、调研并参赛、指定赛事报名、续办提交。默认优先免费、线上、允许现有项目、改造成本低且有目标用户价值的赛事。用户另有偏好时优先遵守。没有数量要求时先集中完成最匹配的一场，其他适合项保留候选；不广撒报名到大量无关赛事。

一开始建立项目专属任务目录与进度记录，使用 [任务档案模板](references/task-record.md)。记录与作品安装包分开，不能把个人联系方式或账号状态写进通用 Skill。恢复时先读档案，再核对官网和已登录页面；不重复报名、建队、发帖或提交。

## 核心判断

- **资格、主题、交付要求先于奖金。** 名称中有 AI、开源或 Skill，不代表当前项目符合。
- **现有项目允许参赛，不等于既有功能算比赛期间成果。** 读取关于既有作品、开发窗口、增量和重复参赛的规定，明确本轮新增工作。
- **报名、组队、作品发布、正式提交和审核通过是不同状态。** 以官网记录分别确认；注册平台账号不算报名，上传市场也不一定完成参赛。
- **演示和文件校验不能替代核心功能实测。** 指定工具必须真实使用，不能虚构开发记录、运行数据或平台集成。
- **集合项目需要具体参赛场景。** 给 Skill-Bible 这类能力库选一个最有说服力的旗舰或可运行工作流；能以整体平台参赛时说明整个平台的用户价值，不能只堆数量。

## 工作流程

### 1. 建立项目事实卡

归集：项目实际解决的问题、目标用户、当前能力、语言/平台、可运行方式、现有演示、创建与版本时间、公开/私有材料和许可范围。区分 `已验证`、`用户提供`、`待验证`，不将 README 宣传语自动当作实测结果。

读取完成任务所需文件，不下载或上传整库私密内容。若给出的是集合仓库，先确定候选旗舰及其必要依赖。

### 2. 搜索并验证当前赛事

使用当前日期和用户时区，按项目类别搜索国内外开发者平台、主办方官网、官方仓库及可信活动索引。先宽搜发现，再逐个验证强候选；聚合页和搜索摘要不作为最终报名依据。

每个强候选核对：主办方、官方报名地址、报名/组队/作品截止及原始时区、当前入口是否开放、身份/地区/年龄限制、团队人数、线下要求、是否允许既有作品、指定模型/工具/接口、文件/视频/发布要求、费用和作品授权条件。重要未知项明确标注，不能先报名再核实资格。

将赛事分为 `可直接推进`、`小幅适配后可投`、`需另做项目`、`资格待确认`、`已截止/未开放`。只把前两类作为本轮执行重点。按主题贴合、规则可满足、剩余时间、适配工作量、用户目标价值排序，给出首选和简短理由。

日期、倒计时和入口状态冲突时，记录冲突并核对官方最新页面或公告。提交未开放时记录实际开放时间，继续准备可完成的材料；只有用户明确要求稍后继续/提醒时才配置真实自动化，不声称会自行醒来。

### 3. 读取提交表，形成最小适配方案

尽早查看真实报名与提交页面，确定必填信息和实际交付规格。使用最小必要的真实改动满足赛题；不要为了参赛把成熟项目改成无关产品。

若必须使用指定平台，先真实加载项目、运行代表场景、修正缺陷并保存输出。区分既有工作与本次新增工作；保留实际工具记录，不生成虚假的“某平台开发全过程”。

已有材料足够时直接执行；仅在规则歧义、核心功能无法验证或用户信息缺失影响资格时提出具体问题。涉及作品重许可、独占授权或整体公开私有项目时，先说明实际变化并取得相应授权，不能默认改许可证。

### 4. 准备并实测材料

按实际表单制作名称、一句话介绍、用户问题、解决机制、创新点、技术实现、启动方式和本次增量。需要时提供截图、演示视频、评审体验方式、仓库版本或上传包，遵守字数、时长、文件数和大小限制。

选能说明核心价值的真实或明确模拟输入跑完整任务，保存输入和实际输出，检查关键判断与事实边界。不可把手写预期答案称为平台实测；没有测量的节省时间、转化率、用户数等不填成成果。

打包时检查目录入口、依赖、许可通知和密钥/私有资料，排除内部记录与真实学生材料等非必要内容。评审链接在合适的未登录环境验证可访问；受控体验账号仅走评审专用字段，不公开个人账号密码。

### 5. 报名、建队与正式提交

优先复用用户已登录的目标账号，通过适用连接器、官方 API/CLI 或浏览器完成操作。遵循当前环境工具与确认规则，不从浏览器外读取会话、令牌或其他凭据。

按真实流程逐步推进：报名 → 组队/选择赛道 → 指定工具适配 → 必要市场或项目发布 → 提交材料 → 最终提交。用户已经授权“直接参赛”的范围内，普通填写、上传和提交不逐步重复请示；未知身份、验证码、费用、协议接受或新的敏感权限按实际动作和环境要求处理，并一次说明当前具体卡点。不要订阅无关营销或开通付费计划。

第三方 Agent 可用于平台开发与验证，但不能把用户资料交给不必要的外部服务；其“已提交”说法要用目标平台的作品链接/状态核验。用模拟输入验证时不要引入用户未授权的真实简历或学生资料。

遇到页面超时、文件下载或上传失败，先核对现有状态再重试。可尝试另一个官方入口、受支持的文件上传或公开源码读取；同一问题连续两次无进展则换路径或说明确切阻塞，不盲目刷新或重复最终提交。不得绕过站点安全机制。

### 6. 核验回执与保存断点

每个会改变外部状态的关键步骤后，取得明确的成功信号。正式提交完成必须核对赛事归属、作品/团队、最终版本、状态及必需附件；保存提交编号或官方链接、时间和可用的页面证据。

更新任务档案，区分 `已报名`、`已建队`、`作品已发布`、`已正式提交`、`待审核`、`需补件`。`待审核`是赛事平台状态，不是另加内部人工批准流程。上传成功但缺少另一必需市场发布时，仍属于未完成。

无法推进时，留下已完成事项、原样错误摘要、未完成事项、续办入口、材料位置及唯一下一步。账号内任务链接标注“需本人登录”，不当公开演示链接。交接给其他 Agent 时保留断点，不让它重做已完成动作。

## 默认交付

给用户一个简短结论：哪场最匹配、实际完成到哪一步、是否正式提交。附精简候选表、参赛材料目录和官方回执。需要用户动作时只列当前真正必需的信息或确认，并说明它如何影响继续；不要重复询问已有答案。

## 外部参考与持续改进

遇到平台流程不熟、市场联动或评审交付不明时，读取 [平台流程参考](references/platform-patterns.md)，再查当前官方帮助与实际表单。检索围绕具体缺口，例如“官方赛事 registration submission requirements existing projects”“平台名 Skill 市场 发布 指南”。重点看报名与提交是否分离、版本怎样生效、既有项目如何声明、多个入口如何关联以及评委访问如何验证。

比较机制能否减少当前漏项和重复动作，再将有效做法接入任务。研究记录、真实失败与修复写入内部维护记录；可泛化的缺陷修正保存到本 Skill 并用原案例复核。赛事名称、截止日和个人信息留在任务档案，不硬编码成通用规则。Skill 被调用时才能执行；没有实际调度器就不承诺后台搜索或自动跟踪。
