# Skill 迭代闭环

将一个信号转成一次可验证的 Skill 改进。外部参考、用户主动反馈、公开聚合数据或评测失败都只是信号，必须先转成可观察的问题。

读取 [迭代记录模板](references/iteration-record.md)。每次只解决一个明确问题，避免把“顺便优化”混入同一版本。

## 工作方式

1. 记录信号来自哪里、发生了什么、可信度如何。
2. 把“用户不喜欢”“Star 很多”改写成可观察症状。
3. 提出一个最小假设，定位可能有问题的规则、输入、输出或资源。
4. 做最小改动。优先改现有 Skill；只有能力边界明显不同才拆新 Skill。
5. 使用 `skill-eval-runner` 或等价案例验证，保留通过和失败证据。
6. 通过后使用 `skill-release-auditor` 检查发布；失败则撤回假设并记录原因。

## 数据边界

只使用用户主动反馈或公开 Issue、平台合法提供的聚合分发数据、匿名化评测案例、公开可访问的 Skill 与文档。

不得追踪用户本地调用，不收集提示词、材料、文件、输出、账号或设备信息。分发数据只说明“被注意到”，不能直接证明 Skill 有效。

## 输出

输出一条完整迭代记录：问题、假设、改动、评测、结论、版本影响和下一次要观察的信号。长期维护时追加到同一份倒序台账。

## 边界

- 高 Star、名人作者或单个好评只用于发现，不直接等于质量。
- 外部 Skill 只借鉴机制；重新表述、重新验证，不复制受限内容。
- 未获得稳定样本前，不展示成功率、满意度或质量分。
