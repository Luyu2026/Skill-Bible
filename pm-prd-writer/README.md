# 可评审 PRD 写作（pm-prd-writer）

## 它适合什么场景

你有一个想法、一段用户反馈、一页会议纪要或一张聊天截图，但还没成文档——研发问边界、设计问流程、业务问价值时，大家各说各话。

它把模糊需求收敛成团队能评审的 PRD：先分清事实、假设与待确认项，再给出方案、边界、验收和还没拍板的事。

## 它解决什么

普通聊天写需求，容易得到一份「功能罗列」——看起来完整，一到评审就被问住。

这个 Skill 替你把三件事做深：
1. **写之前先体检**：需求来源站不站得住、用户价值说不说得清、成功怎么定义——风险提前显性化，而不是写完了才发现
2. **按真实产品结构输出**：五大章节 + 功能模块递归结构，每个功能带用户故事、前置/后置条件、界面交互、异常流程、数据字典
3. **自动补漏 + 待确认项清单**：异常边界、埋点、非功能需求、系统对接逐项自查；所有 **[待确认]** / **[假设]** 汇总成清单，每条带默认建议值，评审会上能直接拍板

## 一个重要机制

**阶段零需求体检**：动笔前 30 秒过三个信号——需求来源（只有"老板说/竞品有"而无用户证据？）、用户价值（说不出现有替代方案？）、成功定义（说不出上线看哪个指标？）。体检不是关卡，用户明确"就是要写"就照写，但风险会写进待确认项首条。

## 你会拿到什么

- 一份**评审版 PRD**：问题定义、用户任务、方案、流程（Mermaid）、边界、验收、指标、待确认项，Markdown 或 docx
- 一份**待确认项清单**：所有假设和缺口，按"必须确认 → 建议确认 → 可后续补充"排序，每条附默认建议值
- 信息确实不足时，你拿到的是**需求梳理文档**（当前理解 + 关键问题 + 方案方向 + 建议下一步），而不是硬凑的半成品

## 怎么开始

把下面这段话发给你的 Agent：

```text
请调用 pm-prd-writer，把下面的需求整理成可评审的 PRD。不要补造事实，先标出必须确认的信息：

【原始需求】
（粘贴你的想法、会议纪要或需求描述）

【已有材料】
（如有：竞品分析、原型图、数据、相关文档链接）
```

## 边界

- 它不替你拍板"这个需求该不该做"——它把风险摆到台面上
- 信息不足时优先问，不虚构数据或用户结论；确实需要假设时，全部标注 **[假设]** 并在待确认项列出
- 适合产品需求文档；纯技术方案、纯 UI 稿标注请用对应的其他 Skill
