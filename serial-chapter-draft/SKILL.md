# 番茄小说单章写作

## 一句话主餐

普通聊天常把片段当章节；本技能把现有设定或上一章接成具有事件闭环和章末牵引的 2200—2800 字正文。

## 输入

- 先读作者设定、分章大纲、上一章末尾和已确定的人物关系。
- 确认本章是首章、承接章还是改稿，不能用同一开头模板处理。
- 确认叙述人称、题材和本章必须发生的事件。
- 默认正文按非空白字符计数，标点计入；平台另有口径时另行报告。
- 缺设定时可创作并标注新增内容；不得宣称掌握平台内部流量机制。

输入处理顺序：
1. 先读取已给材料，复述本轮目标。
2. 只补问会改变执行路线的信息。
3. 可以合理假设的内容单独标记，事实缺口不能伪造。
4. 用户只要演示时明确标“模拟”，不称真实案例脱敏。

## 核心判断

1. 首章优先让读者看见主角处境与异常；续章优先兑现上一章悬念。
2. 本章只推进一个主事件，支线用于增加阻力而非抢占主题。
3. 信息钩子必须对应可继续发生的事，不能每章都靠昏迷或假死。
4. 2200—2800 是本任务交付长度，不将其描述为所有平台的强制规则。
5. 爽点、悬念与情绪选择应服从题材和作者风格，不强塞打脸模板。
6. 正文与章后说明分开计数；不靠重复心理描写填长度。

决策落地要求：
- 每个判断都必须影响本轮的取舍、动作或交付。
- 解释只写到足以让用户理解当前选择，不堆砌理论。
- 用户更正输入时，撤回受影响结论并重做对应部分。

## 编号工作流

### 1. 建立章节账本

- 提取上一章未兑现的问题。
- 锁定人物位置、持有物和已知信息。
- 记录本章要改变的状态。
- 首章从设定中选一个能当场发生的事件。
- 交付：起始状态与结尾状态对照。

### 2. 设计事件骨架

- 写进入事件、尝试、升级、决策、结果。
- 每次升级增加具体成本。
- 确认主角参与推动结果。
- 给每段分配大致篇幅，避免末尾仓促。
- 交付：五段事件骨架。

### 3. 写完整正文

- 以正在发生的行为开场。
- 必要设定嵌入行动或争执。
- 在中段让第一次方案受阻。
- 让主角选择产生可见结果。
- 交付：连贯单章初稿，不以大纲代替。

### 4. 核对连续性

- 逐项查人物知识是否越界。
- 查时间、物件和空间位置是否矛盾。
- 续章兑现前章至少一个承诺。
- 保留尚未解决但有作用的悬念。
- 交付：修正后的正文与连续性更新。

### 5. 计数与重写

- 使用本地脚本或编辑器计数正文非空白字符。
- 不足时补因果环节或必要行动。
- 超长时删重复说明，保留关键决策。
- 再次计数，给出实际口径及结果。
- 交付：2200—2800 字的完整正文；无法计数则标明尚未验证。

### 6. 交付与续接

- 章末留下由本章结果引发的新行动。
- 附本章新增人物与设定。
- 给下一章第一场景一个起点。
- 接收作者对节奏或人设的具体反馈再改稿。
- 交付：正文、计数、连续性账本。

## 直接交付与下一步

- 完整单章正文为主交付，必须与计数范围一致。
- 附篇幅口径、人物状态更新和下一章起点。
- 完成标准：长度合格、事件结果清晰、上一章关键事实无矛盾。
- 本轮暂不安排全书大纲或运营，除非作者明确要求。
- 无文件工具时给正文供用户粘贴计数；不把估计写成已校验。

交付前验收：
- 对照用户原始输入，检查关键事实和目标没有被替换。
- 逐项检查本技能承诺的产物已实际给出，而非只说将会生成。
- 把未确认项写在相应结论附近，不藏在笼统说明里。
- 用户能直接采取下一动作，无需再把输出加工成另一个任务。
- 不宣称访问过未访问的材料，也不宣称运行了未运行的工具。

### 外部参考与延展

- 触发：章节有字数却没有推进、连续两章重复同一冲突，或用户明确要求平台适配。
- 优先读作者已通过审核的稿件和读者反馈；平台事项查番茄作家专区的公开创作与帮助资料。
- 检索“连载 场景推进 章节承诺兑现”，比较悬念兑现、事件密度和人物决策。
- 平台政策和字数规则以当次官方信息为准，不能把创作经验写成推荐算法事实。
- 只采用补足当前因果链的机制；用同一章改前改后和连续性检查验证，不保证签约或收益。

研究后的采用规则：
1. 先记录本轮具体缺口，再选互补机制，不以项目热度决定。
2. 优先复用用户已验证有效的方法；材料已足够时直接交付。
3. 外部机制只能改变执行方法，不能替代用户事实。
4. 新机制先用于当前产物，按上面的验收标准核对。
5. 找不到可靠改进时保留现有可用路径，并如实说明局限。

随附 `demo.md` 是明确模拟的输入与成品，用于理解交付尺度。
实际调用不复用其中的个人事实或把模拟结果当成用户结果。
