# 招聘情报分析框架

用于公司招聘情报、岗位画像和方向地图。分析不是把标题聚类后下结论，而是从可复核的招聘事实推到有限的业务判断。

## 一、样本记录

| 字段 | 记录什么 | 为什么需要 |
| --- | --- | --- |
| 样本编号 | 公司模式用岗位编号；岗位模式用 JD 编号 | 让每条结论可追溯 |
| 来源 | 招聘官网、公开职位页、用户给出的链接或截图 | 判断来源与覆盖范围 |
| 采样日期与范围 | 日期、社招/校招/实习、地区、筛选词、可见页数 | 招聘信息会变化，范围决定结论边界 |
| 公司 / 团队 / 职能 | 页面明确展示的名称 | 识别业务与组织线索 |
| 岗位与边界 | 职位名、城市、年限、是否计入 | 去除不相干或不可比样本 |
| 结果责任 | 这个角色对增长、交付、收入、质量、内容、客户成功等什么负责 | 标题不是工作本身 |
| 工作链路 | 输入/判断 → 行动 → 交付物 → 验收 | 还原实际工作 |
| 能力证据 | 项目、指标、作品、专业经验、工具、协同对象 | 区分“能做”与“会说” |
| 进入门槛 | 学历、年限、地点、语言、到岗、证书 | 判断可投性，不等于业务能力 |
| 原文依据 | 一句关键职责或任职要求 | 避免凭印象归类 |

同一公司、同一岗位族的重复发布只保留一条进入统计；其他保留为背景，但不得把频次抬高。职责只有口号、没有可核对内容的 JD 不作关键证据。

## 二、从招聘事实到判断

每个值得写的判断都按以下格式呈现：

| 层级 | 应该怎么写 | 不该怎么写 |
| --- | --- | --- |
| 事实 | “在可见的 18 条岗位中，7 条来自 AI 数据与评测相关团队。” | “公司全力押注评测。” |
| 推断 | “招聘组合显示该方向正在补充数据、评估与交付能力，可能是产品规模化前的能力建设。” | “公司已经确定下一代产品战略。” |
| 其他解释 | “也可能是存量团队扩招或人员替换，不能仅凭职位数排除。” | 忽略替代解释。 |
| 待验证 | “比较近 90 天新增岗位、团队产品发布和负责人表态。” | 把猜测伪装成结论。 |

## 三、公司招聘情报的信号清单

优先找“岗位组合”而不是单一热门岗位：

- **能力链路是否闭合**：研发之外是否出现数据、评测、设计、产品、交付、售前、运营、合规等角色；
- **细分是否变深**：通用岗位变成特定行业、技术模块或工作流岗位，往往代表工作已从探索进入分工；
- **业务是否外溢**：同一能力从核心产品延伸到客户交付、渠道、海外或终端；
- **协同是否出现**：同一方向同时出现产品、工程、运营和商业角色，通常比单一招聘更值得关注；
- **时间与地域是否集中**：仅当发布时间和地域字段完整时才统计趋势与集中度。

以上都是信号，不是因果证明。公司层面的正确信息密度来自“岗位簇 + 职责原文 + 范围透明”，而不是漂亮但不可验证的数量。

## 四、岗位与方向的分层

对岗位画像或方向地图，固定拆成五层：

1. **结果责任**：这个角色最终要让哪件事变好；
2. **工作链路**：从何种信息出发，做哪些判断和行动，交付什么；
3. **能力证据**：公司需要通过什么事实判断候选人真的做过；
4. **进入门槛**：地区、年限、学历、语言及其他筛选条件；
5. **岗位边界**：标题相近但实际归属不同的角色。

只有前 3 层能进入“用户如何提升”的建议；第 4 层只影响投递范围；第 5 层防止误投与错误学习。

## 五、个人材料的可选映射

用户给出简历、经历或作品后，再加：

| 市场 / 公司需要什么 | 用户已有事实 | 状态 | 最小动作 |
| --- | --- | --- | --- |
|  |  | 已有但未表达 / 做过但需核实数据 / 真实能力缺口 / 仅是招聘偏好 |  |

不要建议用户为了匹配 JD 而编造项目或指标。真实能力缺口要给可完成的最小动作，例如完成一份岗位相关的分析作品、补齐一个项目复盘，或调整投递到相邻岗位族。
