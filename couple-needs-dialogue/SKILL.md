# 伴侣需求沟通

## 一句话主餐

普通聊天容易替一方评理；这里从一次真实互动提取未被表达的需求，写出能开口的对话和一个可观察的共同约定。

## 输入

- 最近一次具体事件、双方原话或聊天节选。
- 关系背景、哪些做法曾有帮助，哪些已被拒绝。
- 本轮希望改变的一件小事及双方可以接受的边界。
- 优先使用用户已有记录；缺少对方观点时只写为可能解释。
- 不需要收集整段私密聊天；只取能解释当前冲突的片段。

### 本轮处理门槛

- 用户希望谈日常陪伴、分担或表达偏好时进入需求协商；刚收到气话时先用短句暂停。
- 只有一方材料时，交付的是用户的提案，不是双方关系诊断。
- 抱怨中的具体动作与其解释分开；不能从“没回消息”推出“不爱”。
- 双方尚未答应的频率、时长和复盘日期只写“建议”，不写“已达成”。
- 对方拒绝身体接触时不以“爱的语言”为理由继续触碰；偏好不能覆盖同意。
- 同一请求被拒后，先问是否有替代动作；不设计不断说服直到同意的话术。

## 核心判断

1. 区分长期需求协商和正在升级的争吵；正在失控时先暂停，延后深入协商。
2. 区分观察、解释、感受和请求；“你不在乎我”属于解释，不能当事实。
3. 爱的语言可作为偏好提问线索，不能据此诊断固定人格或判断谁爱谁。
4. 不冒充查普曼本人，不把生成话术说成其原话或官方治疗方案。
5. 请求必须允许拒绝与协商，不能变成忠诚测试或情绪交换。
6. 有威胁、强迫或暴力迹象时，先关注安全与求助，不安排双方当面对质。

## 编号工作流

### 1. 还原一次互动

- 选最近一次可描述的事件，不概括整段关系。
- 按发生时间列出双方说了什么、做了什么。
- 将“总是”“从来不”替换为本次具体行为。
- 输出事实与解释分栏，不替缺席一方认定动机。

### 2. 定位真正需求

- 从抱怨里提取被陪伴、被分担、被尊重或被回应等需求。
- 检查用户想要的是理解、具体行动还是关系决定。
- 需要时问“什么具体变化会让你感到有帮助”。
- 只选本轮最关键的一项需求，避免旧账清单。

### 3. 找出双方可回应的动作

- 把抽象期待变成一个可观察、可协商的行为。
- 参考双方已有正向互动，不强行套五种类型。
- 说明对方可能的实际限制，但不替对方辩解或承诺。
- 输出首选请求和更轻量的备选请求。

### 4. 写开口与承接

- 用具体事件、个人感受、需要、请求组织一段自然语言。
- 避免“真正爱我就应该”等操控句式。
- 为对方愿意、犹豫、拒绝分别写一句承接。
- 每句只推进一个话题，不用长篇说理压过对方。

### 5. 形成试行约定

- 双方同意后才把请求记为共同约定。
- 写明动作、合适的时机和无法完成时怎么告知。
- 复盘时点按行为发生频率定，不强制统一天数。
- 不同意时保留个人边界，不伪造双方共识。

### 6. 复盘真实回应

- 让用户交回对方实际回应及约定是否发生。
- 区分措辞误解、执行困难和双方目标不一致。
- 前两者调整表达或动作，目标不一致时帮助明确边界。
- 不以一次回应推断关系结局。

### 各步执行与验收细则

- 第 1 步按“时间 / 可见行为 / 用户解释 / 未知信息”整理，删除无材料支持的动机判断。
- 第 2 步把“更关心我”问成“下次出现什么动作，你能确认自己被回应”；只保留一个答案。
- 第 3 步请求至少写明动作和发生场景，例如“晚饭后先听我说今天的一件事”；不强制统一时长。
- 第 4 步将每句“你让我……”检查为个人体验，避免把感受变成归罪；不为了柔和而取消真实边界。
- 第 5 步记录“提案 / 对方原话 / 已同意部分 / 仍有分歧”；只有明确同意部分进入约定。
- 第 6 步按实际执行比较：未理解就改表达，时间不合就改安排，明确不愿就保留分歧与个人边界。

## 直接交付与下一步

- 一段可直接开口的需求表达。
- 三类回应下的承接句与一个可协商动作。
- 已同意的试行约定，或尚未形成共识的具体分歧。
- 完成标准是用户能提出清楚请求，并知道如何接住真实反馈。

### 工具不可用时

- 没有专业测评或外部资料访问能力时，仍可从本次原话完成需求表达，不输出诊断与疗效判断。
- 无法完成的关键检查要写明未验证项，不把计划或草稿称为已完成执行。

### 后续输入与收尾

- 本轮先练一个请求；暂停翻旧账和评判关系全部价值。
- 用户交回对方原话、双方最终同意内容和一次实际执行情况，再进入下一轮。
- 对方不愿讨论时不布置双人作业，改成用户可执行的安排与边界表达。
- [模拟交付](references/delivery-example.md)展示拒绝与替代安排；用它检查是否把猜测写成共识。

### 外部参考与延展

- 触发：爱的语言标签引起争论、话术反复像指责，或相同约定持续无法执行。
- 优先查 Chapman 官方资料的概念边界、CNVC 官方需求与请求教学资料。
- 检索 “love languages preferences request” 或 “observation versus evaluation”。
- 比较偏好探索与观察—需要—请求两种机制，观察哪一步能解释本轮卡点。
- 不因某理论流行便当成科学诊断；涉及疗效主张时查原始研究并标明局限。
- 把采用的方法改写成一个具体问题或请求，用用户原句检查是否减少归因和胁迫。

### 可比较的参考机制

- [CNVC 反馈说明](https://www.cnvc.org/about/feedback-advice)提供观察、感受、需要、请求的表达次序；借其区分机制，不把所有日常交流写成四格术语。
- 与 conflict-first-response 比较：该 Skill 先处理能否接触，本 Skill 只在愿意沟通时推进具体约定。
- 五种爱的语言仅帮助提出偏好问题；若标签与本人反馈矛盾，以本人真实偏好为准，不用分类证明谁错。

### 可执行模拟演示

以下全部为明确模拟输入，不代表任何真实用户的经历或结果。

- 模拟输入：“你下班只顾手机，根本不爱我”，用户想要晚饭时被听见。
- 观察：昨晚晚饭时，对方持续看手机；持续多久未知。
- 需求：吃饭时有一段专心交流，而非证明爱不爱。
- 开口：“昨晚吃饭时你一直看手机，我有些失落。我想和你聊聊今天的事。”
- 请求：“今晚吃饭时，我们能先把手机放旁边，聊一会儿吗？”
- 对方忙：“如果今晚有急事，什么时候聊对你更方便？”
- 对方拒绝：“我听见你现在不想聊，我想知道你愿意用什么方式安排交流。”
- 验收：没有诊断对方、没有虚构共同同意，下一步是带回实际回应。

### 交付前检查

- 用 references/delivery-example.md 的输入走完当前模式，对照关键判断逐项核验。
- 将本轮最终成品与输入事实逐项对照；无依据的新增事实必须删除或标为未知。
- 先检查处理门槛和失败分支，再检查行文与格式；不能用篇幅达标代替可用性。
- 新反馈触发通用修正时保留原案例，比较旧版与新版，再同步 README 和必要示例。
