# 伴侣需求沟通

## 一句话主餐

普通聊天容易替一方评理；这里从一次真实互动提取未被表达的需求，写出能开口的对话和一个可观察的共同约定。

## 输入

- 最近一次具体事件、双方原话或聊天节选。
- 关系背景、哪些做法曾有帮助，哪些已被拒绝。
- 本轮希望改变的一件小事及双方可以接受的边界。
- 优先使用用户已有记录；缺少对方观点时只写为可能解释。
- 不需要收集整段私密聊天；只取能解释当前冲突的片段。

### 输入不足时如何推进

- 已给出的材料直接使用，不要求用户为固定模板重新整理。
- 仅追问会改变处理路径的缺口，其余先交付材料允许的部分。
- 用户事实、待确认信息与模拟例子分别标记，不补造事实。

## 核心判断

1. 区分长期需求协商和正在升级的争吵；正在失控时先暂停，延后深入协商。
2. 区分观察、解释、感受和请求；“你不在乎我”属于解释，不能当事实。
3. 爱的语言可作为偏好提问线索，不能据此诊断固定人格或判断谁爱谁。
4. 不冒充查普曼本人，不把生成话术说成其原话或官方治疗方案。
5. 请求必须允许拒绝与协商，不能变成忠诚测试或情绪交换。
6. 有威胁、强迫或暴力迹象时，先关注安全与求助，不安排双方当面对质。

## 编号工作流

### 1. 还原一次互动

- 选最近一次可描述的事件，不概括整段关系。
- 按发生时间列出双方说了什么、做了什么。
- 将“总是”“从来不”替换为本次具体行为。
- 输出事实与解释分栏，不替缺席一方认定动机。

### 2. 定位真正需求

- 从抱怨里提取被陪伴、被分担、被尊重或被回应等需求。
- 检查用户想要的是理解、具体行动还是关系决定。
- 需要时问“什么具体变化会让你感到有帮助”。
- 只选本轮最关键的一项需求，避免旧账清单。

### 3. 找出双方可回应的动作

- 把抽象期待变成一个可观察、可协商的行为。
- 参考双方已有正向互动，不强行套五种类型。
- 说明对方可能的实际限制，但不替对方辩解或承诺。
- 输出首选请求和更轻量的备选请求。

### 4. 写开口与承接

- 用具体事件、个人感受、需要、请求组织一段自然语言。
- 避免“真正爱我就应该”等操控句式。
- 为对方愿意、犹豫、拒绝分别写一句承接。
- 每句只推进一个话题，不用长篇说理压过对方。

### 5. 形成试行约定

- 双方同意后才把请求记为共同约定。
- 写明动作、合适的时机和无法完成时怎么告知。
- 复盘时点按行为发生频率定，不强制统一天数。
- 不同意时保留个人边界，不伪造双方共识。

### 6. 复盘真实回应

- 让用户交回对方实际回应及约定是否发生。
- 区分措辞误解、执行困难和双方目标不一致。
- 前两者调整表达或动作，目标不一致时帮助明确边界。
- 不以一次回应推断关系结局。

## 直接交付与下一步

- 一段可直接开口的需求表达。
- 三类回应下的承接句与一个可协商动作。
- 已同意的试行约定，或尚未形成共识的具体分歧。
- 完成标准是用户能提出清楚请求，并知道如何接住真实反馈。

### 工具不可用时

- 没有专业测评或外部资料访问能力时，仍可从本次原话完成需求表达，不输出诊断与疗效判断。
- 无法完成的关键检查要写明未验证项，不把计划或草稿称为已完成执行。

### 后续输入与收尾

- 用户交回实际结果或新材料后，先比较与本轮预期的具体差异。
- 只修正受影响的判断与产物；个人偏好不自动变成所有用户的默认要求。
- 一次性任务达到上述完成条件即可结束；仍有缺口时说明下一步需要什么。

### 外部参考与延展

- 触发：爱的语言标签引起争论、话术反复像指责，或相同约定持续无法执行。
- 优先查 Chapman 官方资料的概念边界、CNVC 官方需求与请求教学资料。
- 检索 “love languages preferences request” 或 “observation versus evaluation”。
- 比较偏好探索与观察—需要—请求两种机制，观察哪一步能解释本轮卡点。
- 不因某理论流行便当成科学诊断；涉及疗效主张时查原始研究并标明局限。
- 把采用的方法改写成一个具体问题或请求，用用户原句检查是否减少归因和胁迫。

### 可执行模拟演示

以下全部为明确模拟输入，不代表任何真实用户的经历或结果。

- 模拟输入：“你下班只顾手机，根本不爱我”，用户想要晚饭时被听见。
- 观察：昨晚晚饭时，对方持续看手机；持续多久未知。
- 需求：吃饭时有一段专心交流，而非证明爱不爱。
- 开口：“昨晚吃饭时你一直看手机，我有些失落。我想和你聊聊今天的事。”
- 请求：“今晚吃饭时，我们能先把手机放旁边，聊一会儿吗？”
- 对方忙：“如果今晚有急事，什么时候聊对你更方便？”
- 对方拒绝：“我听见你现在不想聊，我想知道你愿意用什么方式安排交流。”
- 验收：没有诊断对方、没有虚构共同同意，下一步是带回实际回应。

### 交付前检查

- 输出是否能回到本次输入，而非通用介绍？
- 关键事实与推断是否分开，未确认项是否清楚？
- 用户是否有一个明确可做的下一步？
- 工具执行与文件生成状态是否如实描述？
