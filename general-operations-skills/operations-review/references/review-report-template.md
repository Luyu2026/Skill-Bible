# 复盘报告模板

本文件是 operations-review 的参考模板。生成复盘报告时按此结构输出，每个章节的说明文字是写作指引（不要原样复制到最终文档里），根据实际需求填充内容。

---

## 文档头部

```markdown
# [动作名] 复盘报告

复盘时间：（当天）
复盘对象：（活动/项目/月份）
```

---

## 一、结论先行

**作用**：3 句话内说清这次复盘最要紧的结论。

```markdown
## 一、结论先行
- **目标达成**：参与量 8w/10w（80%），转化率 4.2%/5%（84%）
- **最大收获**：老带新邀请机制效果超预期（新客占比 40%）
- **最大教训**：预热期太短，流量峰值后劲不足
```

## 二、目标 vs 结果

**作用**：摆事实。先确认"原定目标是什么"，再谈差距。

```markdown
## 二、目标 vs 结果
| 项 | 原定目标 | 实际结果 | 差距 |
|---|---------|---------|------|
| 核心指标 | 参与量 10w | 8w | -20% |
| 转化率 | 5% | 4.2% | -0.8pp |
| 成本 | 预算 5w | 4.6w | -8% |
```

## 三、归因分析

**作用**：找到"为什么"。每个原因标注证据等级（A 数据支持 / B 强推断 / C 推测）。先数据、再动作、最后环境。

```markdown
## 三、归因分析
**核心发现：**

| 发现 | 证据等级 | 依据 |
|------|---------|------|
| 老带新机制是增长主因 | A 数据支持 | 分享转化率 12%，新客 40% 来自邀请 |
| 预热期不足导致峰值不够 | B 强推断 | 上线首日流量即达峰值，无爬坡 |
| 竞品同期活动分流 | C 推测 | 无明显数据支撑，需验证 |

**5-Why 深入（对最大差距）：**
转化率低于目标 → 用户到支付环节流失 → 支付页加载慢 → 未做性能压测 → 开发排期紧跳过压测 → 测试范围审批不严
```

## 四、经验与教训

**作用**：区分可复用 vs 需规避，写成规则而不是描述。

```markdown
## 四、经验与教训
**可复用（下次照做）：**
- [ ] 老带新邀请机制纳入标准活动模板
- [ ] 活动上线前完成性能压测清单

**教训（下次规避）：**
- [ ] 预热期 ≥ 3 天，设置爬坡检查点
- [ ] 转化路径页面提前 1 周冻结需求
```

## 五、行动项

**作用**：复盘落地关键。3-5 条，每条必须有 Owner 和验收标准，否则等于没写。

```markdown
## 五、行动项
| 优先级 | 行动项 | 类型 | Owner | 验收标准 | 截止 |
|--------|--------|------|-------|---------|------|
| P0 | 修复支付页性能问题 | 止损 | 张三 | 支付页加载 < 2s | 本周 |
| P1 | 沉淀老带新机制为活动模板 | 沉淀 | 李四 | 模板入库 | 2 周内 |
| P2 | 建立预热期标准流程 | 优化 | 王五 | 流程文档 + 检查点 | 下月 |
```

## 六、待验证假设

**作用**：公平对待不确定项。

```markdown
## 六、待验证假设
- [ ] 竞品同期活动分流（验证方式：竞品数据/渠道监测）
- [ ] 用户对"分享得奖励"的敏感度（验证方式：下轮 A/B）
```
